# ADR 0001 — Adoção de Arquitetura em Camadas

**Status:** Aceito
**Data:** 07/08/2026
**Responsável pela decisão:** Geovanna Lima

## Contexto
O Mini Kanban é um sistema de gerenciamento de tarefas em formato de quadro Kanban: cada tarefa (Task) possui um título, descrição, tipo (bug, feature, refactor), prioridade (baixa, média, alta) e um status que representa em qual coluna do quadro ela se encontra (TODO, DOING, DONE).

com prazo curto de entrega, cada membro responsável por uma parte distinta do sistema

Diante disso, Precisávamos de um padrão arquitetural que:

- Fosse simples o suficiente para ser implementado e compreendido por todos
  os membros da equipe dentro do prazo do projeto;
- Permitisse dividir o trabalho entre os membros da equipe sem que um
  bloqueasse o outro (alta coesão, baixo acoplamento entre partes);
- Fosse compatível com o stack definido (Java 17, Spring Boot, PostgreSQL) e
  com o consumo por um frontend externo via API REST;
- Deixasse claro onde cada tipo de responsabilidade (regra de negócio,
  acesso a dados, exposição HTTP) deveria viver, facilitando revisão de
  código e a divisão de commits entre os membros do grupo.

As alternativas consideradas foram:

- **MVC clássico**: mais comum em aplicações com views renderizadas no
  próprio backend. Como o frontend é desacoplado (React consumindo API
  REST), a "View" no sentido tradicional não existe no backend, o que torna
  o MVC redundante em relação à arquitetura em camadas para este caso.
- **Microservices**: desnecessariamente complexo para o escopo de um MVP
  acadêmico com um único domínio (tarefas de um Kanban). Introduziria
  overhead de infraestrutura (múltiplos serviços, comunicação entre
  serviços, orquestração) sem benefício real para um sistema deste porte.
- **Arquitetura em Camadas (Layered Architecture)**: escolhida por separar
  claramente as responsabilidades em camadas horizontais, com dependência
  em uma única direção (Controller → Service → Repository → Domain),
  mantendo o projeto simples e organizado.

## Decisão

Adotar **Arquitetura em Camadas** como padrão arquitetural do backend,
dividido nos seguintes pacotes:

```
com.kanbam.task_manager
├── controller   → Camada de apresentação (REST API)
├── service      → Camada de regras de negócio
├── repository   → Camada de acesso a dados (Spring Data JPA)
├── domain       → Entidades JPA e Enums (núcleo do modelo)
└── dtos         → Objetos de transferência de dados entre API e cliente
```

Regras da divisão de responsabilidades:

- **Controller** não contém lógica de negócio. Apenas recebe requisições
  HTTP, delega para a camada de `service` e devolve a resposta.
- **Service** concentra toda regra de negócio (ex.: toda tarefa nasce com
  status `TODO`). É a única camada autorizada a orquestrar operações entre
  repositórios e a aplicar validações de domínio.
- **Repository** é responsável exclusivamente pelo acesso a dados, usando
  `JpaRepository` do Spring Data. Não contém lógica de negócio.
- **Domain** contém as entidades JPA (`Task`) e os enums de suporte
  (`StatusEnum`, `TipoEnum`, `PrioridadeEnum`), representando o núcleo do
  modelo, sem depender de nenhuma outra camada.
- **DTOs** isolam o contrato da API do modelo interno (entidade JPA),
  evitando que mudanças na entidade quebrem o frontend, e vice-versa.

A dependência entre as camadas segue uma única direção:

```
Controller → Service → Repository → Domain
                  ↑
                DTOs (usados por Controller e Service)
```

## Consequências

**Positivas:**
- Separação clara de responsabilidades, facilitando a divisão de tarefas
  entre os membros da equipe 
- Baixo acoplamento entre camadas: alterações na forma como os dados são
  persistidos (`repository`) não afetam a camada de apresentação
  (`controller`), e vice-versa.
- Alta coesão: cada pacote tem uma única razão para mudar (Single
  Responsibility a nível de camada).
- Facilita testes unitários isolados por camada 
- Ponto de extensão já identificado para o padrão Observer, no método
  `moverTarefa()` da `TaskService`, sem necessidade de alterar outras
  camadas quando essa lógica for implementada.

**Negativas / trade-offs assumidos:**
- Para operações simples (como um CRUD básico), a arquitetura em camadas
  pode parecer verbosa (mais classes/arquivos do que uma solução mais
  direta), mas esse custo foi aceito em troca de manutenibilidade e clareza
  para fins didáticos, que são o foco da disciplina.
- Como todas as camadas dependem, em última instância, do modelo de
  domínio (`Task` e seus enums), qualquer mudança estrutural na entidade
  ainda exige atenção em `service` e possivelmente em `dtos`, mesmo que o
  `controller` e o `repository` não precisem mudar.
- Diferente de uma arquitetura hexagonal/ports-and-adapters, as camadas
  aqui não são totalmente independentes de frameworks (ex.: `domain` usa
  anotações JPA diretamente na entidade). Essa simplificação foi uma
  escolha consciente para reduzir a complexidade, adequada ao escopo do
  MVP acadêmico.
